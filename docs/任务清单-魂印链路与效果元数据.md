## 0. 数据考古结论（已验证的事实，不要重新考证）

1. `monsters.soul_mark_id` 在 `seer_unity.sqlite` 中**全部为 0（死列）**。运行时走这条路的现代精灵全部拿不到魂印。
2. 现代精灵的魂印权威数据在 **`effect_icon` 表**：`pet_id` 是 JSON 数组字符串（如 `"[4911]"`，必须 JSON 解析精确匹配，LIKE 会误中 14911）；`tips` 是魂印完整描述（含富文本标记 `[color=...]`）；`kind`（JSON 数组，如 `[4,8,10]`）是官方分类标签；`args` 是空格分隔参数。
3. `effect_icon.effect_id` **不指向 `new_se.idx`，也不与 `effect_info` 模板文本对应**（2516 在 effect_info 里是减伤模板，不是骑士决斗魂印）。它是引擎内部效果号，本库快照不可解析。魂印文本以 `tips` 为准。
4. 一只精灵可能有多行 effect_icon（如奥菲利娅 4706 有 2291/2344 两条，基础版/强化版），**取 icon id 最大的作为当前生效版本**。
5. `effect_des` 表共 553 条：kind=1（412 条）专属名词/状态词条；kind=2（46 条）异常状态定义；kind=3~5（约 95 条）机制/时点术语（含"执行""免疫对手的攻击""回合开始时"等官方正式定义）。
6. 旧链路（`new_se WHERE idx = soul_mark_id`）对老精灵仍有效，保留为 fallback。
7. 技能效果 id 空间：`Effect.id` / 插件注册 id（如 moves_lib 的 843）与 `effect_info.id` 对齐，可共用一套元数据目录。

## 任务 1：魂印数据链路修复

**目标**：现代精灵（如 4911 星光·艾欧丽娅）在运行时能加载到魂印描述文本与官方分类标签；effect_des 词典可查询。

### 1.1 Repository 层新增（`include/db/official_data_repository.h` + `src/db/official_data_repository.cpp`）

- [x] 新增 `SoulMarkDisplayRecord`：
  ```cpp
  struct SoulMarkDisplayRecord {
      int icon_id = 0;            // effect_icon.id（行主键，多版本取最大）
      int effect_id = 0;          // 引擎内部效果号（原样保留，不解析）
      std::vector<int> kind_tags; // 官方分类标签（kind 列 JSON 解析）
      std::vector<int> args;      // args 列空格分隔
      std::string tips;           // 魂印完整描述（原始富文本）
      std::string tips_plain;     // 去富文本后的纯文本
      std::string come;           // 来源描述
      int monster_id = 0;
  };
  ```
- [x] 新增 `load_soul_mark_display_by_monster(int monster_id)`：遍历 effect_icon，C++ 侧 JSON 解析 pet_id 精确匹配，多行取 icon_id 最大。
- [x] 新增 `TermRecord { int id; int kind; std::string name; std::string description; }` 与查询：`load_term(const std::string& name)`（kinddes 精确→LIKE 兜底）、`load_terms_by_kind(int kind)`。
- [x] `load_terms_by_kind(2)` 作为异常状态名词表（任务 2 分类器要用）。

### 1.2 实体层接入（`src/entities/pet_factory.cpp`、`include/entities/soul_mark.h`）

- [x] `SoulMark` 增加字段：`std::vector<int> kind_tags;`（官方分类）、`int monster_id = 0;`，构造函数带默认参数不破坏旧调用。
- [x] `create_soul_mark_for_pet`：`soul_mark_id > 0` 走旧 new_se 链路；否则走 `load_soul_mark_display_by_monster`，`SoulMark.id = effect_id`（插件函数注册键），description = tips_plain。
- [x] 查不到任何魂印数据时返回空 `SoulMark{}`（与现状一致，不抛错）。

### 1.3 验证

## 任务 2：效果元数据层

**目标**：每个 effect id 可查询语义元数据（类别/概率/固有·命中 class/可否决策略），并提供概率阈值谓词（帝皇铠甲/梅赫维特检测"≤50% 异常附加"用）。**本任务只交付元数据与查询，不改 execute 判定逻辑**（那是"判定门+凭证"任务的事）。

### 2.1 元数据结构（新文件 `include/effects/effect_meta.h`）

- [x] `enum class EffectCategory { Unknown, StatusInflict, StatChange, DamageModify, Heal, Priority, Shield, Drain, Other }`
- [x] `struct EffectChance { int value = -1; int arg_index = -1; }`（-1 = 模板无概率；arg_index 指向 EffectArgs.int_args 下标）
- [x] `enum class EffectClass { Undefined, Inherent, Hit }`（固有/命中，默认 Undefined 等数据标注）
- [x] `struct NullifyPolicy { bool hit_effect_invalidatable = true; bool invalid_compensatable = true; }`
- [x] `struct EffectMeta` 聚合上述 + `std::string source_note`（分类依据，调试用）

### 2.2 目录与分类器（`src/effects/effect_meta.cpp`）

- [x] `EffectMetaCatalog` 单例：`build()` 时从 repository 拉全部 effect_info（2340 条模板），文本规则分类 + 少量人工覆盖表。
- [x] 规则示例：模板含 `{n}%` 且目标位是异常状态名词（effect_des kind=2 词表 + "异常状态"字样）→ StatusInflict，chance.arg_index = n；"改变…等级"→ StatChange；"先制"→ Priority；"恢复"→ Heal；"护盾/护罩"→ Shield；"吸取"→ Drain。
- [x] 人工覆盖表 `kMetaOverrides[]`（如 843 先制、2533 异常附加），规则错时在此修正，不改规则引擎。
- [x] 查询 API：`const EffectMeta* find(int effect_id)`；`bool is_status_inflict_at_most(int effect_id, const EffectArgs& args, int threshold_pct)`（解析 args 得实际概率值再比阈值；概率未知返回 false）。

### 2.3 验证

- [x] 冒烟测试断言：effect 4/5 → StatChange 且 chance.arg_index=1；2533 → StatusInflict 且 `is_status_inflict_at_most(2533, args[100,31,1], 50)` 为真；843 → Priority；未收录 id 返回 nullptr 不崩溃。
- [x] 编译 + 冒烟测试通过。
